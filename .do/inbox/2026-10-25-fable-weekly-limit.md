# Cockpit cannot show the Fable weekly limit

**Status:** needs-triage

Claude.ai's usage page shows a separate Fable weekly limit next to the all-models one. On the user's Team account it read 74 % used against 52 % for all models, both resetting Thu 3:00 PM; on their Max 5x account it read 62 % against 100 %, described as "Up to 50% of your weekly limit" (screenshots in session b5de1086, 2026-10-25). In Claude Code 2.1.310 the response schema parses `unifiedWindows` for `five_hour`, `seven_day` and `seven_day_overage_included` only, and `rateLimitType` knows `seven_day_opus` and `seven_day_sonnet` but no Fable window (`strings` of `~/.local/share/mise/installs/claude/2.1.310/claude`). So `session.measure`'s `rateLimits` likely never carries the Fable limit, and cockpit's pace gauge cannot warn when it is the limit that binds, though cockpit already draws any extra window Claude Code reports (`cockpit/hooks/cockpit.ts:55`). Unverified: what the API actually sends for a Fable-heavy session; check `rateLimits` in a live session that uses Fable.

Verified 2026-10-25 in the beacon session (0550a685), which corrects the paragraph above on the client side and settles the API side for the usage endpoint. The API does send the Fable weekly limit for the Team account: `GET https://api.anthropic.com/api/oauth/usage` with the Claude Code OAuth bearer token (from the keychain item `Claude Code-credentials`, key `claudeAiOauth.accessToken`) and `anthropic-beta: oauth-2025-04-20` returned `five_hour` 47 %, `seven_day` 61 %, `seven_day_opus` and `seven_day_sonnet` null, and a `limits[]` array of three rows: `{kind:"session", percent:47}`, `{kind:"weekly_all", percent:61}` and `{kind:"weekly_scoped", group:"weekly", percent:86, severity:"warning", is_active:true, resets_at:"2026-10-29T13:59:59Z", scope:{model:{id:null, display_name:"Fable"}, surface:null}}`, which matches the usage page's 85 % Fable bar; the Fable row carries no model id, only the display name. The 2.1.310 binary does know this window, which the earlier `strings` pass missed because the header name is a template: its window table is `[["five_hour","5h"],["seven_day","7d"],["seven_day_overage_included","7d_oi"],["overage","overage"]]`, its label map reads `seven_day_overage_included:"Fable limit"`, and its schema describes that window as "overage-included weekly (per-model bucket; present only for accounts whose responses carry that window) ... as read from the anthropic-ratelimit-unified-* response headers"; a present `7d_oi` header becomes a `weekly_scoped` row labelled with the first entry of the allowlist `["Fable","Fable 5","Fable 5.1"]` (GrowthBook flag `tengu_usage_overage_included_models`), the `/usage` dialog renders it as "Current week (Fable)", and the structured usage SDK response (marked experimental) exposes `rate_limits.model_scoped[]` with `display_name`, `utilization`, `resets_at`. The statusline JSON input documents only `rate_limits.five_hour`, `seven_day` and `spend_limit`, and the mod API's `SessionRateLimit.kind` is a free string documented as `five_hour`, `seven_day` or `spend_limit` (`cockpit/.claude-plugin/types/claude-code/index.d.ts:11770`), so whether `session.measure` ever carries a `seven_day_overage_included` window is still unverified; cockpit's probe at `cockpit/hooks/cockpit.ts:50` would draw it as a bare name and percentage if it did. Still unverified: whether message responses carry the `anthropic-ratelimit-unified-7d_oi-utilization` header for this account; a curl to `/v1/messages` with the OAuth token is refused outright (`429 rate_limit_error "Error"`, no unified headers, an `anthropic-workspace-id` header attached), so only a real Claude Code request can show it, for example `ANTHROPIC_LOG=debug claude -p ... --model claude-fable-5-1 2> log` if the bundled SDK's debug logging surfaces response headers, which was not tested. Decision for triage: read the Fable row from the usage endpoint directly in cockpit (one authenticated GET, the same source the `/usage` dialog uses, undocumented and marked experimental on the client side), or wait for `session.measure` to carry the `7d_oi` window.
